# Design Decisions

Short log of deliberate choices. One line each, newest first.

- **DD-031** (2026-06-20) — **Action space trimmed to `[search, list_sources, finish]` — BOTH `expand_*` tools dropped (B1 lean menu WON).** The richer action space failed to earn its keep — and actively hurt. Measured on the v2 set (n=3 full-menu B0 vs n=2 lean B1): **adding `expand_around_chunk` robustly regressed 5 v1-solid questions** (a02/a05/a10 went 3/3→0/3; a12/a17 3/3→degraded) while the tool **never fired reliably on its own meter** (a18: 0/0/1 calls across runs) and **never fixed its target** (a16: 0/3, exits on `budget` even when called) — net NEGATIVE. `expand_document` was **provably dead weight**: 0 calls on all three of its breadth meters (a05/a06/a12) across every run; a06 holds via repeated `search` without it. Dropping both: correctness **0.587→0.643**, faithfulness **0.829→0.930** (the cleanest signal — stripping the distractor tools stopped the controller wandering, so answers stayed grounded), and the two clean tool-tax victims **recovered** (a02/a10 0→2/2). General principle (transferable): **the action space is not free — every tool taxes routing on EVERY question** (bigger system prompt = noisier tool selection), so a tool must clear that noise floor to belong; "might be useful" is not enough, it must be *measurably net-positive*. Both tools kept in the catalogue (`agent/tools.py`) but config-gated OFF (cf. `parent_expansion`), re-enable only behind a properly-prompted A/B. Caveats: lean run is n=2; a05 did **not** recover (a genuine breadth/coverage failure, not a tooling one — next lever); `expand_document`'s removal is mildly confounded with the lean win (B2 = v1's exact menu was the cleaner control, skipped for velocity since the 0-fires-across-5-runs evidence is decisive). New agentic baseline = **B1 lean, 0.643 / faith 0.930** on the v2 (25-Q) set. Faithfulness diagnosis carries forward: failures are **faithful-but-incomplete** (0 hallucinations, failing Qs grade SUPPORTED) → the binding constraint is **decomposition/completeness**, not grounding.
- **DD-030** (2026-06-20) — **Controller router view is a PREFIX snippet — known limitation, relevance-centered fix DEFERRED.** The controller sees each evidence chunk truncated to its first `CONTROLLER_SNIPPET_CHARS=300` chars (`loop.py:router_view`), so a fact in a chunk's *latter half* is invisible to the **routing** model. Decided this is acceptable for now because the split is two-model: the **generator** writes the answer from FULL `hit.text` (`answer.py:assemble_context`, no trim at `answer_char_budget=0`), so a tail fact is lost only to the controller's *view*, not to the *answer* — its impact is routing inefficiency (over-search when the answer is already in hand) and, narrowly, a missed thread in *chained* multi-hop where hop-2's clue sits in hop-1's tail. Mitigation if it ever bites (cheapest→principled): (a) raise the snippet char cap (bigger controller prompt, grows with rounds×chunks); (b) **relevance-centered snippet** — show the query-matching span instead of the prefix, so position-in-chunk stops mattering (standard query-biased-summarization / best-matching-passage IR technique; lexical term-overlap scan is a ~20-line hand-roll, semantic version costs an embed/chunk/round); (c) a `read_chunk` tool whose observation returns full text on demand. **Deferred (YAGNI):** no measured failure traces to controller-blindness yet — revisit only if a run shows the controller finishing/mis-routing *despite* holding the answer-bearing chunk, at which point reach for (b). Noted inline at `CONTROLLER_SNIPPET_CHARS`.
- **DD-029** (2026-06-20) — **Stop-condition redesign (oscillation guard: hard-break → patience + feedback + abstention guard) — WON, new agentic baseline 0.917.** The DD-028 failure audit (`docs/evals/AGENT_FAILURES.md`) found the dominant *process* leak was the oscillation guard firing on a **single** redundant retrieval: `exit=oscillation` runs scored **68%** correct vs `finish` **82%**, and the loop was cutting multi-hop questions off mid-investigation (a10 forced to answer *without* `resolver.md`, one reformulation short). General principle (see `docs/agents/AGENT_LOOP_STOP_CONDITIONS.md`): a stop condition must fire on **global stuckness, not a local stumble** — one redundant query means *reformulate*, not *abort*. Three changes (`agent/loop.py` + `prompts/agent_react.md`): (1) **patience** — `OSCILLATION_PATIENCE=2`, trip only on 2 *consecutive* redundant rounds, reset on any productive retrieval (`max_rounds` stays the hard backstop); (2) **feedback** — annotate the redundant round's observation with a `[NOTE: NO NEW EVIDENCE FOUND …]` marker so the controller *knows* to change course (patience alone is inert at temp 0); (3) **prompt pointer** to that marker. First measured run recovered the targets (a02/a05/a10) but **regressed a08** (abstention 3/3→2/3): patience told grounded-stopping Qs to *keep searching*, and the extra hunt surfaced a distractor (`CHUNK_SIZE 1000`) it answered with instead of refusing — the same global-knob/opposite-capability tension as parent-expansion & completeness. Fixed with a 4th change: an **abstention guard** bullet ("if focused searches keep missing the specific fact, finish and answer 'Not enough information.' — don't broaden to loosely-related results"). **Results (3 runs, final config): correctness mean 0.917 (14–15/16) vs the 0.76 old baseline — new floor = old ceiling; 14/16 Qs robust 3/3; abstention 3/3 robust (a08 fixed); a02/a05/a10 all 3/3; `oscillation` exits → 0 (≈5 redundant rounds/run absorbed).** Cost: controller ~94K tok (up from ~77K — the patience tax; the abstention guard clawed back ~103K→94K by letting refusals finish early). Remaining flaky: **a16** (1/3, synthesis-incompleteness F5) and **a07** (1/3, judge-borderline filename survey F6) — *different* mechanisms, untouched by this lever, the next targets. Supersedes DD-028's 0.615 as the agentic anchor. Caveat: 3 runs (vs ±2-Q variance), but the per-question robustness (14/16 at 3/3) and the structural `oscillation→0` evidence carry it.
- **DD-028** (2026-06-19) — **First AGENTIC baseline established — the new-lineage anchor.** Config (the baseline definition): four-tool action space `[search, expand_document, list_sources, finish]`, `max_rounds=5` (headroom for the agent to compose tools), `answer_char_budget=0` (no final-answer trim), and **`parent_expansion` OFF**. *Parent-expansion-off rationale:* it was a FIXED retrieval-time ±1-neighbour policy that WON DD-020 on the pure-RAG lineage, but under the agentic system the controller can expand on demand (`expand_document`) and auto-neighbour-expansion just inflates context for no agency — turned off as a deliberate baseline choice, re-A/B-able later. The corpus also grew to **22 docs** (a 7-doc workers'-comp claims-ETL domain added alongside the RAG-server docs), so this is the first baseline over a **two-domain** corpus. Eval = `agentic.yaml` (16 Qs, capability-sliced, outcome + L1 trajectory diagnostic via `evals/agentic_eval.py`). **Results: end-to-end correctness 8/13 = 0.615, abstention 3/3, trajectory pass 9/16 = 0.562.** By capability (outcome | trajectory): efficiency **4/5 | 3/5**, decomposition **1/4 | 4/4**, tool_selection **3/4 | 2/4**, grounded_stopping **3/3 | 0/3**. Cost: controller 78K tok / 55 calls (~3.4/Q), generator 47K / 16 calls; ~3.3 rounds/Q. Tool usage across the run: `search` 40, `finish` 10, `expand_document` **2**, `list_sources` **1**. **Mechanism-level findings:** (1) **Decomposition completeness is the binding constraint** (1/4 correct) — the agent DOES take the hops (trajectory 4/4) but the GENERATOR drops second-hop facts in synthesis → INCORRECT (a10/a14/a16); same synthesis-partial failure class as DD-024, now the dominant agentic failure. Whether `parent_expansion`-OFF aggravates multi-hop completeness is an open A/B lever. (2) **The special tools are under-used** — `expand_document` fired only 2× and `list_sources` 1× across 16 Qs; the controller defaults to `search`, so the four-tool space behaves ~like `[search,finish]` in practice, and a06/a12 were answered CORRECTLY *without* `expand_document` (the soft-discriminator caveat realized). Direct evidence for the open "does the richer action space earn its keep / is `expand_document` the right granularity" question (cf. the `expand_around_chunk` idea). (3) **Eval-design finding:** grounded_stopping's `expects_exit: finish` assertion is too strict — all 3 abstentions were CORRECT but reached via the oscillation guard (`exit=oscillation`) after searching for the absent fact, which is GOOD behaviour; the 0/3 trajectory there is an assertion artifact, not an agent failure (fix: accept `oscillation` for abstention, or drop `expects_exit`). (4) Abstention is solid (3/3, no hallucination); mild over-search on 2 efficiency Qs (3 rounds vs asserted ≤2). This 0.615 / 3-3 / 0.562 triple is the anchor every future agentic A/B compares against.
- **DD-027** (2026-06-19) — **Agentic eval cases bind trajectory assertions to raw tool *names*, deliberately (not decoupled).** The new `agentic.yaml` set asserts a good path via `trajectory.expects_tool: <tool>`, which couples the eval case to the tool's *code identifier* (`agent/tools.py`). Two looser alternatives were weighed and **rejected for now as unneeded complexity**: (a) a stable **capability label** declared on each `Tool` (e.g. `expand_document` → `fetch_full_document`) that the registry owns and the loader validates — decouples renames but adds a vocabulary to maintain; (b) **behavioral-effect** assertions (e.g. "full document present in the evidence set") — purest decoupling but needs harness logic and can't cover information-only tools like `list_sources` (no evidence trace). With only 4 hand-rolled tools the name↔capability mapping is ~1:1, so the indirection buys nothing today (YAGNI). General principle acknowledged for the record: this is binding a test to *implementation* rather than to a *stable interface* — fine while tool names are stable, brittle once they churn. **Revisit trigger:** when tool names start changing — most likely **A2 (native tool-calling)**, or when a tool splits/merges or several tools share one capability — promote to the capability-label approach (alternative a). Until then, accept the coupling; the loader should at least validate `expects_tool` against the live registry so a rename fails loudly, not silently. Recorded in `docs/evals/AGENT_EVAL_SETS.md` (Part 2 schema note) too.
- **DD-026** (2026-06-15) — **Stronger embedder (MiniLM-L6 → mpnet-base-v2) — A/B was a NO-OP, reverted.** Swapped the dense embedder `all-MiniLM-L6-v2` (384-dim) → `all-mpnet-base-v2` (768-dim, the higher-quality sibling in the same sentence-transformers family) as a pure config change (no code — both are symmetric, no query-instruction prefix; the asymmetric-bge path that *would* have needed prefix wiring was deliberately avoided for this reason). Re-indexed the corpus (302 chunks, 768-dim) and ran recall + answer-correctness once at the **C4 champion** (hybrid+rerank+parent+agent), judge held at `gpt-oss-20b` for apples-to-apples with the existing C4 anchor. **Result: nothing moved** — recall@5 .950→.950 (identical, same two multi-hop misses q41/q42), MRR .975→.975, correctness **.773→.775** (inside the repeat-to-repeat noise band). **Reverted to MiniLM** (keep-or-revert: mpnet is ~5× the CPU cost per embed for zero measurable gain). Mechanism: at a hybrid+cross-encoder config the **dense embedder is masked** — BM25's keyword leg plus the reranker recover the same top-k chunks regardless of which embedder ranked them first, so upgrading *only* the dense leg is invisible. The binding constraint isn't dense recall (already saturated at .95); it's **synthesis** — the 7–8 PARTIALs are multi-source-completeness failures a better embedder can't touch. Fourth instance of *relevance ≠ answerhood* (cf. DD-014/019/020). Honest caveat: single run vs the 3-repeat anchor, but a .002 move needs no variance work to call flat. Lesson kept: an upgrade to a component that a *downstream* stage already compensates for buys nothing — measure at the *full* pipeline, not the component in isolation. Points the next lever at the bottleneck that's actually binding: query transformation (decomposition/multi-query) for the multi-source partials, or a stronger reranker.
- **DD-025** (2026-06-14) — **Role-tiered agent: separate `controller` and `generator` models.** The agent loop used ONE model (flash-lite) for both the routing decisions (`decide_next_action`, called ~5×/question) and the final answer (`generate_from_scratchpad`, 1×/question). Split them into distinct config roles (`llm.roles.controller`, `llm.roles.generator`) threaded through `run_agent`/`Answerer`/`build_answerer` (controller defaults to the generator when unset, so the champion is unchanged — both still flash-lite). Motivation: **model tiering** — spend the expensive model only where the hard work is. The DD-024 failure audit found our remaining failures split 4 *synthesis* (fact was in context, generator under-wrote it — q25/q31/q39/q41) vs 4 *coverage* (fact never retrieved — q22/q26/q27/q42); the synthesis half is a **generator** problem, motivating an A/B putting the generator on `gemini-2.5-pro` (one pro call/Q) while the controller stays cheap. Also split the cost instrumentation (DD-024) by role — `usage_record(controller, generator, judge)` — because the roles can now be different-priced models, and the per-role meter already shows the **controller** is the larger spend (~5 calls + ~8K tok/Q vs the generator's 1 call + ~5K), which is exactly why pro-on-controller would be the costly bet and pro-on-generator the cheap one. Wiring shipped + smoke-tested; the pro-generator A/B is the pending experiment.
- **DD-024** (2026-06-14) — **Per-run token-cost instrumentation (Module 5 pulled early).** Quality is one axis; cost/latency is an orthogonal one — DD-022/023 kept *narrating* cost ("~3–4× latency", "bound 18×") without measuring it. Now every eval run records token usage. **Fork resolved: Option A (widen the return), not B (hidden meter)** — `complete()` returns `Completion(text, usage: Usage)` instead of a bare `str`, so cost is an explicit, visible property of each call (no spooky side-effect state) and threads honestly through retries/fallback (you count the call that actually answered). `Usage{calls, prompt_tokens, completion_tokens}` adds, so a per-call usage rolls up to per-question (the agent loop sums controller calls + final answer onto `AnswerResult.usage`) and per-run. **Tokens, not dollars** (provider-neutral count vs a drifting price table) and **near-zero variance** at temp 0 — a quieter meter than the LLM-judge score. **Two buckets kept SEPARATE on purpose** (`usage_record`): `generator` = system cost you'd pay in production; `judge` = instrument cost with no production counterpart — never summed, or $/query would ~2×. Recorded both run-level and per-question in the eval JSON; a console line prints generator tokens + **calls/Q** (the cost of agency: naive=1, agentic≈6 on q01 — and it counts controller *retries*, otherwise-invisible real spend). Pure instrumentation — can't regress quality, so no eval gate; sanity-checked on a 1-Q smoke run.
- **DD-023** (2026-06-14) — **Module 3 context-selection A/Bs — all three LOST; the plain arrival-order budget trim is the champion** (kept negative results; granular runs in EXPERIMENTS.md). Vs the agentic champion (.800/.975 correctness/faithfulness, gen flash-lite / judge gemini-2.5-pro): **(a) controller self-curation** (controller emits a `keep` list on finish; snippet 300→700 so it can judge, not just recognize) — LOST .800→.750, citation-hallucinations 0→3: snippet-based pruning *over-prunes* (kept 1-of-9), starving the generator — trades a transparent miss for a **silent, confident** one. **(b) round-robin-by-source** (best chunk of each source, then 2nd of each…) — LOST as a trade-off .800→.725, faithfulness .975→**1.000**: fairness across sources kills every *wrong* answer (perfect grounding) but caps same-source slots, so multi-part answers lose completeness — and it fights parent-expansion (DD-020). **(c) remove the budget** (`answer_char_budget` 16000→0, keep all chunks) — also LOST to .725 / faithfulness 1.000, the *same* number from the opposite direction: extra evidence *diluted* answers (all grounded, fewer parts covered) rather than completing them. **Reverted to 16000.** Reframe: the 16k trim began as a Groq 6K-token-per-request survival hack, but on Gemini's ~1M context it's now incidentally a **quality filter** — arrival order keeps early on-topic chunks and drops late second-hop accretion. Reinforces DD-019 — score is comparable *within* a source, not *across* — so neither a global sort nor a fairness cap is a free win. Caveat: single run (.800 vs .725 ≈ 3 Qs), direction reproduced across two independent interventions.
- **DD-022** (2026-06-14) — **Agentic loop (Module 2) — A/B WON, default ON.** The answer path can now be a hand-rolled **ReAct** (reason→act) loop (`agent/loop.py`, prompt `prompts/agent_react.md`) instead of one fixed retrieval: a controller LLM reads a compact router-view of the scratchpad and emits a single JSON action — `search(query)` (reformulate + retrieve, dedup into the scratchpad) or `finish` — bounded by a `max_rounds=3` budget (circuit breaker) with oscillation/budget stop conditions; the final answer is char-budgeted (`select_within_budget`, `agent.answer_char_budget`) so the accumulated context fits the per-request token ceiling. `Answerer`/`build_answerer` switch naive↔agentic via `agent.enabled`; both evals call the switch and stamp an `agent` snapshot into the run record (`runs.py:agent_config_snapshot`). **Matched A/B** (gen `gemini-2.5-flash-lite`, judge `gemini-2.5-pro` on BOTH arms): correctness **.750→.800** (answered 36→40), faithfulness **.944→.975**, **false-abstentions 4→0**. Mechanism: the loop *retries* (searches again with a reformulated sub-query) where the naive generator gave up — both gains trace to the same 4 recovered answers, which came in grounded. Honest cost: one new INCORRECT (q26 — stated ChromaDB uses 1536 dims, should be 384), and ~3–4× latency (multiple generator calls/question). **[Corrected 2026-06-14 by the DD-024 failure audit:** q26 was originally written up here as a *synthesis conflation* ("more context = more surface to cross-wire"). A deterministic in-context check disproved that — `384`/`all-MiniLM` were **never retrieved**; only `1536` was in front of the model, so it's a **coverage gap** (the answer-bearing chunk didn't come back), not a generation bug. Lesson: don't infer the failure *type* from the symptom; check whether the fact was even in context. See the audit in DD-024 / EXPERIMENTS.]** **Single A/B**: the *direction* is structural (the loop literally can't false-abstain on a recoverable Q), the *magnitude* (±1–2/40) is within this metric's run-to-run noise — variance re-run is an open lever. Default flipped OFF→ON. Hand-rolled deliberately (no LangGraph) to learn what the framework abstracts.
- **DD-021** (2026-06-14) — **Gemini added as primary generator; router goes multi-tier (supersedes DD-004's Groq-only).** Added a `GeminiProvider` (google-genai unified SDK) as a second router tier; `provider_order: [gemini, groq]` and per-role `{provider, model}` resolution (`role_provider_model`) so a role picks its provider+model and the rest of `provider_order` is automatic fallback (a missing key just drops that tier). **Generator = `gemini-2.5-flash-lite`** on the paid `GOOGLE_API_KEY`: this is what unblocked Module 2 — Groq's free tier has a **6K-tokens/request wall** that 413'd the agent's accumulated scratchpad, while paid Gemini gives ~1s/call + ~1M context with no per-request throttle. **Judge = `gemini-2.5-pro`** (stronger than the flash-lite generator; same family, so some self-eval bias remains but it **cancels in an A/B** since both arms share it — for a clean *absolute* faithfulness number re-judge cross-family when the Groq `gpt-oss` bucket resets). Gemini-specific handling baked into the provider: thinking disabled on flash (`thinking_budget=0`, else it eats `max_output_tokens` and truncates) but capped (512) on pro which has a nonzero minimum; system prompt → `system_instruction`; assistant role → `"model"`; transient-drop retry with exponential backoff + jitter (the SDK doesn't auto-retry like Groq's). Consequence: the retired Groq 8b/`gpt-oss` `.775/.850` anchor is **no longer matched** — the agentic A/B re-baselined naive-on-Gemini first (see EXPERIMENTS.md). Embeddings stay local (DD-004 unchanged — neither provider is the embedder).
- **DD-020** (2026-06-14) — **Parent-child expansion (small-to-big) — WON, adopted.** New retrieval stage 3 (`ParentExpansionRetriever` + `store.fetch_source_chunks`): after reranking to top_k child chunks, expand each into its ±`window` contiguous neighbours (same source) and merge into one overlap-trimmed "parent" window for the generator. **Neighbour auto-merge** variant — reuses the existing chunk store, no second-level chunking. Targets the completeness partials (split tables/lists) by restoring contiguous *local* context WITHOUT adding cross-topic distractors — the win a bigger top_k couldn't get (it added separately-ranked distractors, DD-017). A/B (scout held constant, window=1): answer-correctness **0.690→0.759** (CORRECT 20→22), **reproduced ×2 on both arms**; retrieval recall unchanged (source-level guardrail). Default ON. Honest limits: same-source only, so cross-*document* completeness needs are unaffected (q27's extra models live in another doc); parents are larger (~3k vs ~800 chars) → more generation tokens. `window` is an eval-gated knob (window=2 untried).
- **DD-019** (2026-06-14) — **Reranker relevance gate A/B — LOST, removed** (negative result; code deleted as dead code after the A/B). Added a RELATIVE relevance gate to the cross-encoder (`rerank.score_margin`: keep only hits within N logits of the top hit, cap at top_k → may return <top_k, cutting distractors). Relative not absolute because cross-encoder logits are uncalibrated/model-specific (same reason RRF fuses on ranks). Calibrated margin from the score spread (margin≥6 prunes ~nothing; margin=4 prunes 8/29). **margin=4 lost:** guardrail recall@5 1.000→0.966 (one multi-hop 2nd doc pruned); answer-correctness (scout, same-session) **0.690→0.655** — it *did* cut a distractor (INCORRECT 1→0) but the same cut pruned a needed multi-hop chunk (+1 false abstention). Root insight: a second-hop chunk is **legitimately lower-relevance** (it answers the *other* sub-question), so it's indistinguishable from a distractor by relevance score — *relevance ≠ answerhood*, the reranker's ceiling again. No margin sweet-spot for this corpus (4 too aggressive, 6 inert). Also note: same-config baseline came in at 0.690 vs the prior 0.724 — pure run-to-run noise, reinforcing "treat 1-question deltas as noise." Experiments now logged in `docs/EXPERIMENTS.md`.
- **DD-017** (2026-06-14) — **Recursive chunking A/B — recursive LOST, kept fixed** (a kept negative result). Added a format-agnostic recursive splitter (`recursive_chunk` in `chunking.py`: separator hierarchy paragraph>line>sentence>word>char, then merge-to-size with overlap; hand-rolled, dependency-free) behind `retrieval.chunking.strategy`, and A/B'd it vs the fixed-size baseline on two meters, generator held constant (scout). **Both regressed.** Guardrail (retrieval recall, deterministic): recall@3 0.931→0.862, @5 1.000→0.862, **multi_hop@5 1.000→0.333**. Real test (answer-correctness, scout/gpt-oss, rerank+completeness held fixed): **end-to-end 0.724→0.655**, and it **reintroduced 3 false abstentions (q04/q22/q26)** that reranking had eliminated — *and did not fix the q25/q27 completeness it was meant to.* Root cause: at the SAME `chunk_size=800`, recursive breaks at natural boundaries before filling, yielding smaller chunks (304 vs 262) → each doc's content spreads over more chunks → multi-hop docs lose the top-5 competition. Lessons kept: (1) measure — the "obviously better" technique lost; (2) **strategy and `chunk_size` are coupled**, so a one-variable swap can mislead (recursive may need a larger chunk_size); (3) the real lever for fact-level completeness is **parent–child (small-to-big)**, not recursive splitting (which can't keep an over-size table/list whole either). Code kept (off by default) for a future, properly-tuned retry. **top_k follow-up:** a free depth-10 probe confirmed the recursive regression was a coverage (not ordering) problem — every failing multi-hop question's 2nd doc sat at rank 6–8, so multi_hop recall@5=0.333 but **recall@10=1.000**. But raising `top_k` to 8 did NOT rescue end-to-end: **recursive@8=0.655** (false-abstentions 3→1 but those answers came back INCORRECT) and the control **fixed@8=0.655 < fixed@5=0.724** — extra chunks added distractors that turned corrects into partials. Net lesson: `top_k=5` was already well-tuned; the binding constraint flips from coverage (k=5) to precision/distraction (k=8). Champion stays **fixed chunking @ top_k=5 = 0.724**; the real completeness lever remains parent–child, not more/smaller chunks.
- **DD-018** (2026-06-14) — **Self-describing eval records.** Every run JSON now embeds a `config` block (shared `retrieval_config_snapshot()` in `evals/runs.py`): retrieval mode, rerank on/off + model, chunk strategy/size, top_k, hybrid rrf_k/candidate_k, embedding — plus, for answer-correctness, generator/judge model + temperature/max_tokens. The retrieval record reflects the ACTUAL mode/rerank used (derived from the retriever name, so `--mode/--rerank` overrides are recorded faithfully). Motivation: a run must be reproducible/interpretable from the file alone, not guessed from the timestamp — essential once many A/B runs accumulate (DD-013/14/17 all produced near-identical-looking files distinguished only by config).
- **DD-016** (2026-06-14) — **Ungraded ≠ incorrect** (eval measurement integrity). `parse_verdict` previously fell through to a conservative `INCORRECT` when the judge returned an empty/off-format response — silently scoring a *correct* answer as a failure (it sank q13 falsely in the DD-015 run). Fixed: unparseable judge output → `UNGRADED`; `judge_correctness` re-asks up to `JUDGE_MAX_ATTEMPTS=3` (most empties are transient) before giving up; `report()` lists ungraded SEPARATELY (not as failures) and **excludes them from the end-to-end denominator** (`graded = answerable − ungraded`), so an instrument failure counts as neither success nor failure. General principle: a measurement you couldn't take is *missing data*, not a *failing result* — same as test-error vs test-failure, `null` vs `0`. Protects the integrity of every number the eval reports.
- **DD-015** (2026-06-13) — **Completeness rule in the answer prompt** (`prompts/answer_with_citations.md`). The dominant remaining answer-layer failure after reranking was PARTIAL: multi-part questions where the answer stated some facts and dropped others (lists missing items, sequences missing the last step, hedged numbers). Added an explicit "answer COMPLETELY — include every relevant item/step/specific the CONTEXT provides; state definitive facts definitively, don't hedge" rule, reconciled with the existing concision rule (completeness = all relevant facts FROM CONTEXT, not padding). Isolated A/B (rerank held ON): **end-to-end 0.655→0.724, CORRECT 19→21, PARTIAL 9→6**; consistent with intent (partials→corrects). Caveat: metric is non-deterministic — one of the new INCORRECTs (q13) was an EMPTY judge response graded INCORRECT by the conservative fallback (a harness-robustness gap: empty/unparseable judge output should be retried or marked ungraded, not scored INCORRECT), the other (q26) was generation variance.
- **DD-014** (2026-06-13) — **Cross-encoder reranking** — stage 2 of two-stage retrieval (`rag/rerank.py`, `RerankRetriever` wrapper over dense/hybrid; `retrieval.rerank` config; eval `--rerank/--no-rerank` flag). General pattern: a cheap-and-wide bi-encoder/BM25 first stage recalls a candidate pool, then an expensive-and-precise **cross-encoder** re-scores each (query, chunk) PAIR jointly (full attention over both — sees what the indexable bi-encoder can't) and keeps the best top_k. Targets the "right doc, wrong chunk" misses document-level recall can't see. Model `cross-encoder/ms-marco-MiniLM-L-6-v2` (local, CPU, no new dep). **A/B vs hybrid won every cutoff: recall@1 0.724→0.759, @3 0.793→0.931, @5 0.897→1.000, MRR 0.903→0.948** (multi_hop@5 0.667→1.000). Default flipped OFF→ON. Trade-off bought: latency (one forward pass per candidate, candidate_k=20) for precision; recall@5 now saturated (1.0) so @1/MRR + the answer-layer eval are the discriminators going forward.
