# Design Decisions

Short log of deliberate choices. One line each, newest first.

- **DD-019** (2026-06-14) — **Reranker relevance gate A/B — LOST, kept off** (negative result; code retained). Added a RELATIVE relevance gate to the cross-encoder (`rerank.score_margin`: keep only hits within N logits of the top hit, cap at top_k → may return <top_k, cutting distractors). Relative not absolute because cross-encoder logits are uncalibrated/model-specific (same reason RRF fuses on ranks). Calibrated margin from the score spread (margin≥6 prunes ~nothing; margin=4 prunes 8/29). **margin=4 lost:** guardrail recall@5 1.000→0.966 (one multi-hop 2nd doc pruned); answer-correctness (scout, same-session) **0.690→0.655** — it *did* cut a distractor (INCORRECT 1→0) but the same cut pruned a needed multi-hop chunk (+1 false abstention). Root insight: a second-hop chunk is **legitimately lower-relevance** (it answers the *other* sub-question), so it's indistinguishable from a distractor by relevance score — *relevance ≠ answerhood*, the reranker's ceiling again. No margin sweet-spot for this corpus (4 too aggressive, 6 inert). Also note: same-config baseline came in at 0.690 vs the prior 0.724 — pure run-to-run noise, reinforcing "treat 1-question deltas as noise." Experiments now logged in `docs/EXPERIMENTS.md`.
- **DD-017** (2026-06-14) — **Recursive chunking A/B — recursive LOST, kept fixed** (a kept negative result). Added a format-agnostic recursive splitter (`recursive_chunk` in `chunking.py`: separator hierarchy paragraph>line>sentence>word>char, then merge-to-size with overlap; hand-rolled, dependency-free) behind `retrieval.chunking.strategy`, and A/B'd it vs the fixed-size baseline on two meters, generator held constant (scout). **Both regressed.** Guardrail (retrieval recall, deterministic): recall@3 0.931→0.862, @5 1.000→0.862, **multi_hop@5 1.000→0.333**. Real test (answer-correctness, scout/gpt-oss, rerank+completeness held fixed): **end-to-end 0.724→0.655**, and it **reintroduced 3 false abstentions (q04/q22/q26)** that reranking had eliminated — *and did not fix the q25/q27 completeness it was meant to.* Root cause: at the SAME `chunk_size=800`, recursive breaks at natural boundaries before filling, yielding smaller chunks (304 vs 262) → each doc's content spreads over more chunks → multi-hop docs lose the top-5 competition. Lessons kept: (1) measure — the "obviously better" technique lost; (2) **strategy and `chunk_size` are coupled**, so a one-variable swap can mislead (recursive may need a larger chunk_size); (3) the real lever for fact-level completeness is **parent–child (small-to-big)**, not recursive splitting (which can't keep an over-size table/list whole either). Code kept (off by default) for a future, properly-tuned retry. **top_k follow-up:** a free depth-10 probe confirmed the recursive regression was a coverage (not ordering) problem — every failing multi-hop question's 2nd doc sat at rank 6–8, so multi_hop recall@5=0.333 but **recall@10=1.000**. But raising `top_k` to 8 did NOT rescue end-to-end: **recursive@8=0.655** (false-abstentions 3→1 but those answers came back INCORRECT) and the control **fixed@8=0.655 < fixed@5=0.724** — extra chunks added distractors that turned corrects into partials. Net lesson: `top_k=5` was already well-tuned; the binding constraint flips from coverage (k=5) to precision/distraction (k=8). Champion stays **fixed chunking @ top_k=5 = 0.724**; the real completeness lever remains parent–child, not more/smaller chunks.
- **DD-018** (2026-06-14) — **Self-describing eval records.** Every run JSON now embeds a `config` block (shared `retrieval_config_snapshot()` in `evals/runs.py`): retrieval mode, rerank on/off + model, chunk strategy/size, top_k, hybrid rrf_k/candidate_k, embedding — plus, for answer-correctness, generator/judge model + temperature/max_tokens. The retrieval record reflects the ACTUAL mode/rerank used (derived from the retriever name, so `--mode/--rerank` overrides are recorded faithfully). Motivation: a run must be reproducible/interpretable from the file alone, not guessed from the timestamp — essential once many A/B runs accumulate (DD-013/14/17 all produced near-identical-looking files distinguished only by config).
- **DD-016** (2026-06-14) — **Ungraded ≠ incorrect** (eval measurement integrity). `parse_verdict` previously fell through to a conservative `INCORRECT` when the judge returned an empty/off-format response — silently scoring a *correct* answer as a failure (it sank q13 falsely in the DD-015 run). Fixed: unparseable judge output → `UNGRADED`; `judge_correctness` re-asks up to `JUDGE_MAX_ATTEMPTS=3` (most empties are transient) before giving up; `report()` lists ungraded SEPARATELY (not as failures) and **excludes them from the end-to-end denominator** (`graded = answerable − ungraded`), so an instrument failure counts as neither success nor failure. General principle: a measurement you couldn't take is *missing data*, not a *failing result* — same as test-error vs test-failure, `null` vs `0`. Protects the integrity of every number the eval reports.
- **DD-015** (2026-06-13) — **Completeness rule in the answer prompt** (`prompts/answer_with_citations.md`). The dominant remaining answer-layer failure after reranking was PARTIAL: multi-part questions where the answer stated some facts and dropped others (lists missing items, sequences missing the last step, hedged numbers). Added an explicit "answer COMPLETELY — include every relevant item/step/specific the CONTEXT provides; state definitive facts definitively, don't hedge" rule, reconciled with the existing concision rule (completeness = all relevant facts FROM CONTEXT, not padding). Isolated A/B (rerank held ON): **end-to-end 0.655→0.724, CORRECT 19→21, PARTIAL 9→6**; consistent with intent (partials→corrects). Caveat: metric is non-deterministic — one of the new INCORRECTs (q13) was an EMPTY judge response graded INCORRECT by the conservative fallback (a harness-robustness gap: empty/unparseable judge output should be retried or marked ungraded, not scored INCORRECT), the other (q26) was generation variance.
- **DD-014** (2026-06-13) — **Cross-encoder reranking** — stage 2 of two-stage retrieval (`rag/rerank.py`, `RerankRetriever` wrapper over dense/hybrid; `retrieval.rerank` config; eval `--rerank/--no-rerank` flag). General pattern: a cheap-and-wide bi-encoder/BM25 first stage recalls a candidate pool, then an expensive-and-precise **cross-encoder** re-scores each (query, chunk) PAIR jointly (full attention over both — sees what the indexable bi-encoder can't) and keeps the best top_k. Targets the "right doc, wrong chunk" misses document-level recall can't see. Model `cross-encoder/ms-marco-MiniLM-L-6-v2` (local, CPU, no new dep). **A/B vs hybrid won every cutoff: recall@1 0.724→0.759, @3 0.793→0.931, @5 0.897→1.000, MRR 0.903→0.948** (multi_hop@5 0.667→1.000). Default flipped OFF→ON. Trade-off bought: latency (one forward pass per candidate, candidate_k=20) for precision; recall@5 now saturated (1.0) so @1/MRR + the answer-layer eval are the discriminators going forward.
- **DD-013** (2026-06-13) — **Role-aware LLM models** (generator vs judge). `llm.roles` maps a role to a model override (`build_llm(config, role=...)`, `role_model()` helper); no override falls back to `models.<provider>`. Generator = `llama-3.3-70b-versatile`, **judge = `openai/gpt-oss-120b`**. Two wins from one change: (1) **separate Groq daily-token buckets** — Groq meters TPD per-model, and 70b's is the tightest in the free tier (100K TPD vs gpt-oss-120b's 200K), so moving judging off the generator's bucket roughly **2x's answer-correctness runs/day**; (2) a **different-family judge removes the self-eval bias** documented in DD-011. `answer_correctness.py` now builds two LLMs and reports both model names; the report line flags whether self-eval bias is active (it isn't, with the default split). Provider layer stays single-tier router-shaped (overrides are model names on the active provider). General principle: under a per-model quota, the model's TPD ceiling *is* your iterations/day — spend the strong model only where the answer is born.
- **DD-012** (2026-06-13) — Harness observability + LLM resilience. **Logging:** `logging_setup.configure_run_logging(category)` writes a per-run file under `logs/<category>/` (ingestion, evals — gitignored) at DEBUG with full `time/level/name` format, plus a clean message-only console handler; noisy libs (httpx/chromadb/sentence_transformers/groq…) quieted to WARNING. Module loggers added at the meaningful boundaries (ingest, retriever, embeddings, provider, evals); LLM completions log token counts + latency (groundwork for cost/latency tracking). **Retry/backoff:** rely on the Groq SDK's built-in exponential backoff + jitter (429/5xx/timeout, honors Retry-After) rather than hand-rolling — exposed via config `llm.max_retries=5` / `timeout=30`. Layer separation: SDK retries the same provider; `LLMRouter` falls through to the next provider only after retries are exhausted.
- **DD-011** (2026-06-13) — **Answer-correctness eval** — rung 2 (`evals/answer_correctness.py`; named for what it measures — correctness + abstention, NOT faithfulness, which is a separate later eval; see `docs/evals/ANSWER_QUALITY.md`): per question, a deterministic abstention check (answerable must answer, q10-q12 must refuse) + an **LLM-as-judge** correctness verdict (CORRECT/PARTIALLY_CORRECT/INCORRECT) of the generated answer vs the verified `expected_answer`. Ground truth first re-verified 32/32 against the corpus by a fresh-context subagent. **Baseline: end-to-end success 19/29=0.655, abstention 3/3.** Failures cross-validate retrieval: false-abstentions q01/q25/q26 are the retrieval gaps; q22 INCORRECT is a hallucination (claimed ChromaDB hybrid/BM25 search — corpus denies it), motivating a faithfulness judge next; 5 partials are multi-part questions. Honest caveats recorded in-file: judge = generator model (self-eval bias), and LLM output is non-deterministic (this metric has run-to-run variance, unlike recall).
- **DD-010** (2026-06-13) — Naive **RAG answer pipeline** (`rag/answer.py`): hybrid-retrieve top_k → stuff source-labeled chunks into a versioned prompt (`prompts/answer_with_citations.md`) → Groq generates a grounded, cited answer; abstains with exactly "Not enough information." when context is insufficient. Not agentic yet (no retrieve→reason→retrieve loop/budget). Verified: answers+cites when the fact is in-context, abstains for out-of-corpus (q10) AND in-corpus-but-not-retrieved questions. **Key finding:** building generation exposed that **document-level recall@k overstates true answerability** — q01's source doc is "retrieved" (recall passes) but the specific fact-bearing chunk ranks below top-5, so the system correctly abstains. Motivates the answer-quality eval (rung 2) and chunk-level retrieval/chunking work. Adds groq + python-dotenv deps; reads GROQ_API_KEY from gitignored `.env`.
- **DD-009** (2026-06-13) — **Hybrid retrieval** (dense + **BM25**, fused by **Reciprocal Rank Fusion**, rrf_k=60, candidate_k=20) added behind `retrieval.mode`, A/B'd against eval v2, made the default. Beats dense across the board: **recall@1 0.621→0.724, @3 0.759→0.793, @5 0.862→0.897, MRR 0.843→0.903**; BM25's keyword match fixes dense's findability misses (q16 rank −→1, q17 4→1). BM25 via the **rank_bm25** library (user preference: trusted library + explanatory comments over hand-rolling a standard algorithm — superseded an initial hand-rolled BM25); sparse index built in-memory from `store.all_chunks()` each run (fine at this scale). **Default flipped dense→hybrid.** Remaining @5 misses for reranking next: q05, q25, q29.
- **DD-008** (2026-06-13) — Hardened the eval set to **v2**: added q13–q32 (now 29 answerable + 3 abstention), built by a fresh-context subagent that read the full corpus and verified every `expected_sources` against the docs. Goal achieved — recall@5 fell from a saturated **1.000 → 0.862**, giving the metric headroom. New naive baseline: **recall@1=0.621, @3=0.759, @5=0.862, MRR=0.843** (n=29). Genuine, doc-verified failures now exist to tune against: q16 (expected doc not in top-5 — findability), q22/q26/q29 (multi_hop/match:all — second doc missing). Three candidate questions were dropped where the corpus contradicts itself (no defensible ground truth). Supersedes DD-005's 12-question v1.
- **DD-007** (2026-06-13) — Retrieval-recall eval (`src/agentic_rag/evals/`): scores `seed.yaml` against the ingested store, no LLM. Reports recall@**{1,3,5}** + **MRR**, not a single recall@5, because recall@5 over the 11-doc corpus saturates at 1.0 (no headroom — only catches regressions); stricter cutoffs + ranking-sensitive MRR discriminate. Scores **only questions with `expected_sources`** (recall is undefined otherwise) — abstention cases are out of scope here, deferred to a later answer-layer eval. Each run persists a JSON to `eval_runs/` (gitignored) for diffable deltas. **Naive baseline: recall@1=0.667, @3=0.889, @5=1.000, MRR=0.889**; hard case q05 (multi_hop/match:all).
- **DD-006** (2026-06-13) — Naive ingestion pipeline (`src/agentic_rag/rag/`): per-document discover→chunk→embed→store, one doc at a time. Idempotency via a **content-hash tracker** (sha256 of file bytes, not the reference MCP server's mtime/size — avoids git-checkout false re-embeds and size-preserving missed edits) with full new/changed/**deleted** re-indexing. Store = **ChromaDB** (persistent, cosine HNSW); embeddings passed in from local `all-MiniLM-L6-v2` (Chroma is store-only, not embedder). Chunking = fixed-size char windows (800/100) with whitespace snap. All naive baselines, eval-gated for later upgrade. Adds first deps (pyyaml, sentence-transformers, chromadb).
- **DD-005** (2026-06-13) — Seed corpus = curated 11-doc subset of `DocumentationRetrievalMCPServer/docs` (copied/frozen into `corpus/`, not referenced live), chosen for cross-document multi-hop + an Azure-vs-ChromaDB distractor tension; remaining ~29 docs reserved to exercise incremental re-indexing later. Seed eval set `evals/datasets/seed.yaml` v1 = 12 questions (9 answerable + 3 abstention); schema adds `match` (any/all) and `should_abstain` for unambiguous recall scoring.
- **DD-004** (2026-06-13) — Groq-only for the LLM (`llama-3.3-70b-versatile` for agent/judge); fast LPU inference suits the eval loop. Embeddings **stay local** (`all-MiniLM-L6-v2`) because Groq has no embeddings endpoint (text-gen + Whisper only) — local is also the low-hardware-friendly choice. Layer stays router-shaped. Supersedes DD-003's Gemini choice.
- **DD-003** (2026-06-11) — Gemini-only for now (`gemini-2.5-flash` for agent/judge); embeddings stay local (`all-MiniLM-L6-v2`) to save quota. Layer kept router-shaped. Supersedes "Claude as primary."
- **DD-002** (2026-06-11) — Installable `src/` package via `pyproject.toml`; deps single-sourced there (no requirements.txt); `config/`/`prompts/`/`corpus/`/`evals/` versioned.
- **DD-001** (2026-06-11) — Evals are built early, alongside the naive baseline (not deferred); retrieval scored separately from answers.
